# REVIEW.md

Below is every defect I found in the starter app/main.py (helpers and endpoints), with where it was, what was wrong, how I noticed it and how I fixed it.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | MongoClient setup (line 27) | The MongoClient was created without tz_aware set to True. Because of that, MongoDB gave back dates as naive datetimes with no timezone, and Python refuses to compare those with UTC or IST datetimes. | I compared a stored punch_in value with the current UTC time and Python crashed with TypeError: can't compare offset-naive and offset-aware datetimes. | I added tz_aware=True to the MongoClient so every datetime that comes out of MongoDB is clearly marked as UTC. |
| 2 | compute_work_hours (line 70) | It used Python's built-in round(), which rounds half to the nearest even number (banker's rounding). But R4 and R8 asked for normal round half up. | round(2.675, 2) was gave 2.67 when it should be given 2.68, and round(2.5) gave 2 when it should have given 3. | I wrote a small round_half_up() helper using the Decimal module with ROUND_HALF_UP and used it inside compute_work_hours. |
| 3 | compute_overtime (lines 75 to 94) | It ignored the 30 minute minimum from Rule R3. Any extra minutes counted as overtime, even if it was only a few. | Punching out 10 minutes after shift end gave 10 minutes of overtime when it should have given 0. | I added a check so that if the extra time is under 30 minutes that is 1800 seconds, the function returns 0. |
| 4 | compute_overtime (lines 75 to 94) | Overnight shifts were not handled. When shift_end is the same as or earlier than shift_start, the shift end was placed on the same calendar day, so the next morning's punch out was compared against the wrong day. | For an overnight shift, a punch out at 06:40 AM gave 1,480 minutes of overtime (more than 24 hours) instead of 40 minutes. | I added a shift_start parameter and push the shift end date forward by one day whenever shift_end is not after shift_start. |
| 5 | compute_late_minutes (lines 59 to 67) | It used .replace(hour=h, minute=m) directly on a UTC datetime. Setting the IST shift time on a UTC timestamp breaks the subtraction. It also had no date_str, so the shift start was never tied to the actual attendance date. | An employee who punched in at 10:15:59 for a 09:30 shift was reported as 0 minutes late, because the math came out negative and the function returned 0 for everyone. | I passed in date_str, built the shift start for that exact date in IST, compared it with the UTC punch_in, and only counted late minutes when the delay is more than 10 minutes (600 seconds). |
| 6 | GET /health (lines 243 to 248) | It always returned a hardcoded status ok without checking whether MongoDB was reachable. The contract says 200 only when MongoDB answers and 503 otherwise. | I stopped MongoDB and the health endpoint still returned 200. | I wrapped a ping to the database in try and except. If the ping works it returns status ok, and if it fails it raises HTTPException with 503 and the message Database unavailable. |
| 7 | Startup configuration (lines 32 to 53) | No indexes were created at startup, so the collections only had the default _id index. Queries on around 100k documents did full collection scans, and duplicates could slip in when requests ran at the same time. | I listed the indexes on the employees collection and only _id_ was there. Explain output showed COLLSCAN instead of IXSCAN. | I added an init_db function and called it from the FastAPI lifespan. It creates unique indexes on emp_code and on emp_code plus date, along with the query indexes. |
| 8 | POST /employees (lines 251 to 259) | Race condition on duplicate emp_code. The code did find_one and then insert_one, so two requests at the same moment could both pass the check, and the second insert blew up with a 500 instead of a 409. | I sent two requests at once to create EMP0001 and the second one failed with an unhandled DuplicateKeyError and a 500 response. | I wrapped insert_one in try and except for DuplicateKeyError, so the unique index violation now returns 409 Conflict. |
| 9 | POST /employees (lines 135 to 148) | There was no validation of the emp_code pattern (EMP followed by 4 to 6 digits), and shift_start equal to shift_end was accepted. The response also leaked MongoDB's internal _id and returned created_at in the wrong format. | I sent emp_code abc and a shift of 09:00 to 09:00 and both were accepted. The response contained an _id field. | I added a regex check for emp_code and a Pydantic validator for the shift times. I also added serialize_employee_doc, which removes _id and returns created_at as integer epoch milliseconds. |
| 10 | GET /employees (lines 151 to 168) | The skip was calculated as page times page_size. With page 1 that skipped the first 20 employees, so the first page was never returned. | I called GET /employees with page=1 and page_size=20 and the first 20 employees were missing. | I changed the skip to (page minus 1) times page_size. |
| 11 | GET /employees (lines 151 to 168) | The total came from count_documents on an empty filter, so it counted the whole collection and ignored the department filter. There was also no sort on emp_code, and page_size had no limit. | Filtering by department Sales returned the total number of employees in the company instead of the Sales count. | I count with the same query used for the search, added a sort on emp_code ascending, and limited page_size to between 1 and 100. |
| 12 | POST /attendance/punch-in (lines 208 to 226) | There was no check that the employee exists, so an unknown employee caused a 500 with a KeyError on shift_start. It also ignored the overnight rule R1, where a punch before shift end (like 01:30 AM) belongs to the previous day's attendance. | I sent a punch in for EMP9999, which does not exist, and the server returned 500. A night shift punch in at 01:30 AM was saved against the current day instead of the shift date. | I added a 404 when the employee is not found, and a determine_attendance_date helper that gives overnight punches before shift end the previous calendar day. |
| 13 | POST /attendance/punch-in (lines 208 to 226) | Another check and then insert race, this time on emp_code and date, using find_one followed by insert_one. The response also leaked an internal id string instead of using integer epoch milliseconds for times. | Two punch ins sent at the same time could both get past find_one. The response had an id field holding a long string. | I now rely on the unique index for emp_code and date, catch DuplicateKeyError and return 409 Conflict, and build the response with serialize_attendance_doc. |
| 14 | GET /attendance (lines 230 to 257) | It loaded every matching record into memory with list(find(q)) and then sorted and paged in Python instead of letting MongoDB do it. It also did not validate the dates (date_from later than date_to, or bad formats) and leaked the id field. | With a very large collection (say 100,000 logs) it used a lot of memory and was slow. Sending date_from 2026-07-10 and date_to 2026-07-01 did not return a 422. | I moved sorting and paging into MongoDB using sort on date descending then emp_code ascending, with skip and limit. I added 422 errors for bad date ranges, formats and statuses, and used serialize_attendance_doc for the output. |

### Things I looked at and decided were NOT defects

1. Page starting at 1. Normally lists start at 0, but Rule R10 says the page starts at 1, so the default of page = 1 is correct.
2. The default shift times of 09:30 and 18:30. I checked the schemas in openapi.yaml and these exact defaults are what the API contract asks for.
3. Returning an empty items list with a total of 0. When a filter such as department matches nothing, an empty list with total 0 is normal REST behaviour and matches the OpenAPI spec.
