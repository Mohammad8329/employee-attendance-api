# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `client = MongoClient(...)` (line 22) | MongoClient was missing `tz_aware=True`. MongoDB returns dates as naive datetimes without timezone info, which causes Python to throw errors when comparing against UTC or IST datetimes. | Tried comparing `doc['punch_in'] < datetime.now(timezone.utc)` and Python crashed with `TypeError: can't compare offset-naive and offset-aware datetimes`. | Added `tz_aware=True` to `MongoClient` so every datetime coming out of MongoDB is explicitly marked as UTC. |
| 2 | `compute_work_hours` (line 41) | Used Python's built-in `round()`, which does Banker's rounding (rounds to the nearest even number). Rule R4 and R8 strictly require arithmetic round half-up. | Running `round(2.675, 2)` gave `2.67` instead of `2.68`. Also `round(2.5)` rounded down to `2` instead of up to `3`. | Wrote a `round_half_up` helper using Python's `Decimal` module with `ROUND_HALF_UP` and plugged it into `compute_work_hours`. |
| 3 | `compute_overtime` (lines 46–49) | Two bugs: 1) It gave overtime for any extra minutes, ignoring Rule R3's 30-minute minimum threshold. 2) It didn't take `shift_start`, so for overnight shifts (like 22:00 to 06:00) it calculated shift end on yesterday's date, comparing morning punch-out with yesterday morning. | Punching out 5 minutes late gave 5 minutes overtime instead of 0. For an overnight shift, punching out at 06:40 AM gave 1,480 minutes (over 24 hours!) of overtime instead of 40 minutes. | Added `shift_start` parameter, added +1 day to shift end date when `shift_end <= shift_start`, and added a check to return 0 if overtime is less than 30 minutes. |
| 4 | `compute_late_minutes` (lines 33–38) | It used `.replace(hour=h, minute=m)` on UTC datetimes. Changing the hour of a UTC timestamp directly to IST shift time broke the subtraction math completely. Also lacked `date_str` to pin shift start to the attendance date. | An employee punching in 45 minutes late (at 10:15:59 for a 09:30 shift) got calculated as 0 late minutes because the negative math made the function return 0 for everyone. | Passed `date_str`, built `shift_start_dt` on that specific date in IST, compared against UTC `punch_in`, and only counted late minutes if strictly greater than 10 minutes (600 seconds). |
| 5 | `GET /health` (lines 123–125) | The endpoint just returned a hardcoded `{"status": "ok"}` without checking if MongoDB was actually reachable. Contract specifies 200 only if MongoDB answers, otherwise 503. | If MongoDB was stopped or unreachable, `/health` still returned 200 OK. | Wrapped `client.admin.command("ping")` in a try/except block. If ping passes, returns `{"status": "ok"}`; if it fails, raises `HTTPException(503, "Database unavailable")`. |
| 6 | Startup configuration (lines 28–48) | No database indexes were created on startup. The database only had the default `_id` index. This causes full collection scans (`COLLSCAN`) on 100k docs and allows duplicate inserts under race conditions. | Ran `db.employees.list_indexes()` and saw only `_id_`. Queries on large collections would be slow and fail the `IXSCAN` explain check. | Created an `init_db()` function and hooked it up to FastAPI's `lifespan` to automatically create unique indexes (`emp_code`, `emp_code + date`) and query indexes on startup. |
| 7 | `POST /employees` (lines 135–148) | Missing schema validation on `emp_code` pattern (`^EMP\d{4,6}$`) and allowed `shift_start == shift_end`. If two duplicate employee codes were inserted simultaneously, it crashed with an unhandled 500 error instead of returning 409 Conflict. Also leaked MongoDB's internal `_id`. | Sent an invalid `emp_code="abc"` and `shift_start="09:00", shift_end="09:00"`; both succeeded. Triggering a duplicate `emp_code` threw an unhandled 500 PyMongo `DuplicateKeyError`. | Added Pydantic model validator for shift times, regex validation for `emp_code`, wrapped `insert_one` to catch `DuplicateKeyError` and return 409, and added `serialize_employee_doc` to strip `_id` and return `created_at` as epoch ms. |
| 8 | `GET /employees` (lines 151–168) | The pagination `skip` was written as `page * page_size`, meaning `page=1` skipped the first 20 employees and missed page 1 completely! Also, `total` ran on the entire collection ignoring the `department` query filter, `emp_code` sort order was missing, and `page_size` was unbounded. | Queried `GET /employees?page=1&page_size=20` and the first 20 employees were missing. When filtering by department, `total` returned total company employees instead of department count. | Fixed skip calculation to `(page - 1) * page_size`, added `.sort("emp_code", 1)`, set `page_size` max bound to 100, and filtered `count_documents(q)`. |
| 9 | `POST /attendance/punch-in` (lines 208–226) | Had a check-then-act race condition (`find_one` then `insert_one`), had no employee existence check (crashed with 500 if employee didn't exist), ignored overnight shifts in date mapping (Rule R1), leaked internal `"id"` string in response, and didn't serialize timestamps to epoch ms. | Sent punch-in for non-existent employee `EMP9999` and server threw 500. A punch-in at 01:30 AM for a night shift mapped to the current day instead of the shift date. Response contained `"id": "..."`. | Added 404 check for employee, integrated `determine_attendance_date` for overnight shifts, handled race condition by catching `DuplicateKeyError` on unique `(emp_code, date)` index returning 409, and serialized response via `serialize_attendance_doc`. |
| 10 | `GET /attendance` (lines 230–257) | Major memory leak: it fetched every single matching log into Python memory with `list(db.attendance_logs.find(q))` and sorted them in Python RAM instead of delegating to MongoDB. It also lacked validation for `date_from > date_to`, allowed invalid date formats, and leaked `"id"` fields. | On a large collection (e.g., 100,000 logs), this consumed huge amounts of RAM and caused slow response times. Passing `date_from="2026-07-10"` and `date_to="2026-07-01"` did not raise 422. | Replaced in-memory sorting and pagination with MongoDB native `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`, added 422 validation for date ranges/formats/statuses, and used `serialize_attendance_doc`. |

### Anything examined and decided was NOT a defect:
* **`page` starting at 1:** In standard arrays we start at 0, but Rule R10 explicitly states `page starts at 1`. So `page: int = 1` default is correct.
* **`shift_start` and `shift_end` defaults (`"09:30"` and `"18:30"`):** Checked `openapi.yaml` schemas; these exact defaults are requested by the API contract.
* **Returning an empty list `items: []` with `total: 0`:** When a search filter (like department) finds nothing, returning an empty array with 0 total is standard REST practice and matches the OpenAPI spec.
