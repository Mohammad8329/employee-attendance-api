# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `client = MongoClient(...)` (line 22) | MongoClient was missing `tz_aware=True`. MongoDB returns dates as naive datetimes without timezone info, which causes Python to throw errors when comparing against UTC or IST datetimes. | Tried comparing `doc['punch_in'] < datetime.now(timezone.utc)` and Python crashed with `TypeError: can't compare offset-naive and offset-aware datetimes`. | Added `tz_aware=True` to `MongoClient` so every datetime coming out of MongoDB is explicitly marked as UTC. |
| 2 | `compute_work_hours` (line 41) | Used Python's built-in `round()`, which does Banker's rounding (rounds to the nearest even number). Rule R4 and R8 strictly require arithmetic round half-up. | Running `round(2.675, 2)` gave `2.67` instead of `2.68`. Also `round(2.5)` rounded down to `2` instead of up to `3`. | Wrote a `round_half_up` helper using Python's `Decimal` module with `ROUND_HALF_UP` and plugged it into `compute_work_hours`. |
| 3 | `compute_overtime` (lines 46–49) | Ignored Rule R3's 30-minute minimum threshold. Any extra minutes were counted as overtime, even if less than 30 minutes. | Punching out 10 minutes late gave 10 minutes overtime instead of 0. | Added a threshold check returning 0 if `delta_seconds < 30 * 60`. |
| 4 | `compute_overtime` (lines 46–49) | Did not account for overnight shifts (`shift_end <= shift_start`, e.g. 22:00 to 06:00). It calculated shift end on the same calendar day, comparing next morning's punch-out with yesterday morning. | For an overnight shift, punching out at 06:40 AM gave 1,480 minutes (over 24 hours!) of overtime instead of 40 minutes. | Added `shift_start` parameter and added `+1` day to shift end date when `shift_end <= shift_start`. |
| 5 | `compute_late_minutes` (lines 33–38) | It used `.replace(hour=h, minute=m)` on UTC datetimes. Changing the hour of a UTC timestamp directly to IST shift time broke the subtraction math completely. Also lacked `date_str` to pin shift start to the attendance date. | An employee punching in 45 minutes late (at 10:15:59 for a 09:30 shift) got calculated as 0 late minutes because the negative math made the function return 0 for everyone. | Passed `date_str`, built `shift_start_dt` on that specific date in IST, compared against UTC `punch_in`, and only counted late minutes if strictly greater than 10 minutes (600 seconds). |
| 6 | `GET /health` (lines 123–125) | The endpoint just returned a hardcoded `{"status": "ok"}` without checking if MongoDB was actually reachable. Contract specifies 200 only if MongoDB answers, otherwise 503. | If MongoDB was stopped or unreachable, `/health` still returned 200 OK. | Wrapped `client.admin.command("ping")` in a try/except block. If ping passes, returns `{"status": "ok"}`; if it fails, raises `HTTPException(503, "Database unavailable")`. |
| 7 | Startup configuration (lines 28–48) | No database indexes were created on startup. The database only had the default `_id` index. This causes full collection scans (`COLLSCAN`) on 100k docs and allows duplicate inserts under race conditions. | Ran `db.employees.list_indexes()` and saw only `_id_`. Queries on large collections would be slow and fail the `IXSCAN` explain check. | Created an `init_db()` function and hooked it up to FastAPI's `lifespan` to automatically create unique indexes (`emp_code`, `emp_code + date`) and query indexes on startup. |
| 8 | `POST /employees` (lines 135–148) | Check-then-act race condition on duplicate `emp_code`. Two simultaneous requests both saw `find_one` return None, causing the second insert to crash with an unhandled 500 error instead of 409 Conflict. | Fired two simultaneous requests creating `EMP0001`; second request threw an unhandled 500 PyMongo `DuplicateKeyError`. | Wrapped `insert_one` in a `try/except DuplicateKeyError` block to catch the unique index violation and cleanly return 409 Conflict. |
| 9 | `POST /employees` (lines 135–148) | Missing schema validation on `emp_code` pattern (`^EMP\d{4,6}$`) and allowed `shift_start == shift_end`. Also returned `created_at` as ISO string or datetime object and leaked MongoDB's internal `_id`. | Sent `emp_code="abc"` and `shift_start="09:00", shift_end="09:00"`; both succeeded. Response contained `_id`. | Added Pydantic model validator for shift times, regex validation for `emp_code`, and added `serialize_employee_doc` to strip `_id` and return `created_at` as integer epoch ms. |
| 10 | `GET /employees` (lines 151–168) | The pagination `skip` was written as `page * page_size`, meaning `page=1` skipped the first 20 employees and missed page 1 completely! | Queried `GET /employees?page=1&page_size=20` and the first 20 employees were missing. | Fixed skip calculation to `(page - 1) * page_size`. |
| 11 | `GET /employees` (lines 151–168) | `total` ran on `count_documents({})`, counting the entire collection ignoring the `department` query filter. Also, `emp_code` sort order was missing, and `page_size` was unbounded. | When filtering by `department="Sales"`, `total` returned total company employees instead of department count. | Fixed count to `db.employees.count_documents(q)`, added `.sort("emp_code", 1)`, and bounded `page_size` between 1 and 100. |
| 12 | `POST /attendance/punch-in` (lines 208–226) | Had no employee existence check (crashed with 500 `KeyError: shift_start` if employee didn't exist), and ignored Rule R1 overnight shifts mapping punches before shift end (e.g. 01:30 AM) to yesterday's attendance date. | Sent punch-in for non-existent employee `EMP9999` and server threw 500. A punch-in at 01:30 AM for a night shift mapped to the current day instead of the shift date. | Added 404 check for employee, and added `determine_attendance_date` helper to correctly assign overnight punches before shift end to the previous calendar day. |
| 13 | `POST /attendance/punch-in` (lines 208–226) | Check-then-insert race condition on `(emp_code, date)` using `find_one` followed by `insert_one`, and leaked internal `"id": str(res.inserted_id)` string in response instead of integer epoch ms. | Concurrent punch-ins could bypass `find_one`. Response contained `"id": "..."`. | Relied on the unique `(emp_code, date)` compound index, caught `DuplicateKeyError` returning 409 Conflict, and serialized the response with `serialize_attendance_doc`. |
| 14 | `GET /attendance` (lines 230–257) | Major memory leak: it fetched every single matching log into Python memory with `list(db.attendance_logs.find(q))` and sorted them in Python RAM instead of delegating to MongoDB. It also lacked validation for `date_from > date_to`, allowed invalid date formats, and leaked `"id"` fields. | On a large collection (e.g., 100,000 logs), this consumed huge amounts of RAM and caused slow response times. Passing `date_from="2026-07-10"` and `date_to="2026-07-01"` did not raise 422. | Replaced in-memory sorting and pagination with MongoDB native `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)`, added 422 validation for date ranges/formats/statuses, and used `serialize_attendance_doc`. |

### Anything examined and decided was NOT a defect:
* **`page` starting at 1:** In standard arrays we start at 0, but Rule R10 explicitly states `page starts at 1`. So `page: int = 1` default is correct.
* **`shift_start` and `shift_end` defaults (`"09:30"` and `"18:30"`):** Checked `openapi.yaml` schemas; these exact defaults are requested by the API contract.
* **Returning an empty list `items: []` with `total: 0`:** When a search filter (like department) finds nothing, returning an empty array with 0 total is standard REST practice and matches the OpenAPI spec.
